## 2026-09-15 · 0.1.43 Windows 11 上 Alt 列选松开后仍消失、输入诊断记录

- 背景：0.1.42 之后 Windows 10 实测正常，Windows 11 仍会在松开鼠标后丢失列选。本机为 Windows 10（10.0.19045），无法在 Windows 11 上直接复现，公开资料中也没有找到两者在 Chromium 输入事件上的差异说明。逐一排查了会清空列选的全部代码路径（按键、组词、不带 Alt 的鼠标按下、方向键与 Esc、粘贴、事件与行选择）：列选的绘制与焦点无关，失焦不会清除；无边框窗口没有菜单栏，松开 Alt 也不会进入菜单模式。剩下两条可能被其他系统上的输入法触发的路径，现已收紧：
  - 组词：0.1.42 只忽略空组词。若输入法在编辑区获得焦点或被点击时发起的组词本身带有文字，`compositionupdate`/`compositionend` 仍会退出列选。现在只有在列选建立之后按过会输入的键（输入法接管的按键报告为 `Process`，keyCode 229），组词才退出列选；按住 Alt 时的按键不计入。不经键盘的输入（语音、手写）仍会结束列选：带 ProseMirror `composition` 标记的正文改动会退出列选，而不改动正文的组词不会。
  - 按键：列选模式下任何带 Alt 的非修饰键都会退出列选，因此输入法或 Windows 在按住 Alt 时把按键报告为 `Process`（keyCode 229）或 `Unidentified`，也会被当作 Alt 快捷键清除列选。现在这两类以及 AltGraph、CapsLock 等修饰键不再退出列选；Alt+字母、方向键、Home、Ctrl 快捷键（复制、剪切、粘贴除外）照旧退出。
- 新增输入诊断记录：编辑器常驻记录最近 400 条与列选有关的输入事件（按键、组词、鼠标按下与松开、beforeinput、焦点、选区变化），以及列选开始、拖动结束和每一次清除（附调用位置）。按 Ctrl+Shift+F12（视图菜单“导出输入诊断记录”）写入配置目录下的 `diagnostics\input-trace-<时间>.txt` 并在资源管理器中显示；文件头包含应用版本、Windows 版本号、Electron/Chromium 版本与显示器缩放。记录不含正文：可打印按键记为 `char`，组词与输入内容只记长度。若 Windows 11 上仍能复现，导出的记录可以直接指出是哪个事件结束了列选。
